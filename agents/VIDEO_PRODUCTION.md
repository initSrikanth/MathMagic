## Reusable production sequence
1. Establish the exact topic, year level, intended page/section, teaching objective, coverage and user-authorised output. Inventory existing approved footage, audio, boards, scripts and final files first. Keep working players live.
2. Create a reviewed scene manifest: narration text/audio range, start/end timestamps, mathematical statements, graphical assets, highlights and persistent reading windows. Use clear child-facing language and a concept/scene coverage matrix. Validate all calculations using exact rational arithmetic, including equal-size wholes, shading, conversions and comparisons.
3. Generate mathematics programmatically with Python/Pillow, SVG or suitable deterministic tools. Every displayed fraction, including number-line labels, captions, summaries and feedback, must have numerator above a horizontal bar and denominator below. Never expose slash/diagonal notation. Keep mixed-number spacing clear and all diagrams readable on mobile.
4. Use HeyGen only for approved teacher narration/avatar rendering, never mathematical diagrams. Prefer existing approved material. For a needed new render, require explicit paid-generation authorisation, reviewed exact script, verified look/voice/engine compatibility, output plan and spend cap. Use the approved connected authentication or a configured secret binding. Never put credentials or signed media URLs in source, logs, docs, commits, workflow inputs or browser code.
5. Record a content hash and job ID before polling. A timeout or uncertain write outcome requires a status lookup, never a second creation request. Honour retry delays, bound read retries, stop on failure/cancellation and report it. No automatic rerenders, voice auditions, new looks or avatars.
6. Obtain actual narration timestamps by listening/alignment and inspect every scene boundary, start and ending. Graphics must track each spoken mathematical change, with time for reading and thinking. Estimated weights alone cannot establish sync. Do not truncate narration to fit a board or leave a single equation throughout. Preserve approved teacher audio unless a change is authorised.
7. Composite at 1920×1080, preserving aspect ratio and approved geometry. Decode genuine VP9 alpha with an alpha-capable decoder when using transparent footage; inspect bounds across moving frames, not one crop only. Never stretch the teacher, clip head/shoes or use destructive black chroma keying. Export MP4 H.264, yuv420p, AAC, faststart; tune compression against legibility and voice clarity. Existing 720p compositor/QA dimensions need an authorised implementation update before new 1080p production.
8. Retain reversible source footage, graphics, scene manifest, scripts, dependencies, provenance, timestamps and output checksums. Do not store expiring media URLs as durable source identities.

## QA and publication gates
Report actual commands, file/hash, tested SHA, sample counts and observed PASS/FAIL/BLOCKED/NOT RUN results. Fix introduced issues; distinguish existing failures and external limitations.

- Mathematical QA: exact values, equal parts/wholes, every visual statement, no notation leaks and correct intended lesson scenes.
- Content/timing QA: map every narration concept to a visual; inspect every cue boundary and persistent reading window, full beginning/end, audio intelligibility, clipping/silence and sync drift. Frame samples alone do not certify full narration alignment.
- File QA: verify real nonempty MP4 bytes, 1920×1080 dimensions for new outputs, duration, H.264/yuv420p and AAC streams, complete FFmpeg decode, faststart and appropriate file size/bitrate. No arbitrary compression target may make mathematics unreadable.
- Playback QA: metadata, advancing playback, seek early/middle/late, end handling, HTTP byte ranges/content type, fallback URL and desktop/tablet/mobile containment. Test Safari/iOS or a real device before claiming that compatibility; mobile Chromium alone does not establish it.
- Website QA: use responsive native controls, playsinline, metadata preload, typed MP4 source, accessible name and fallback; no autoplay. Captions/transcripts must be accurate. Run applicable existing architecture, generator, resource-coverage and Playwright checks; preserve all five Fractions lesson explainers and total established coverage. Test real auth/progress separately when claiming integration; isolated UI adapters are not production evidence.
- Publication: only after authorised production and passing QA, upload the actual MP4 via the established GitHub asset pattern, check repository/file-size limits and normal Git tracking (not an unserved LFS pointer), verify bytes/hash on the intended branch, then change only the intended section. Preserve authentication, entitlement, quizzes, progress, styles and unrelated content. Do not use the older five-lesson batch publisher for a one-lesson task.
- Follow canonical branch/PR/CI rules for application work. Verify the Pages deployment for the exact publication SHA, then the live MP4 URL, byte ranges, playback, seeking and intended lesson placement. Workflow success alone is not playback proof. Keep rollback scoped to the video/player; retain the previous working resource until replacement is verified. Report commit and deployment separately.
